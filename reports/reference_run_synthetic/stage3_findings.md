> «как должен выглядеть результат», а не реальные показатели датасета.

2 930 отмываний); пороги настраиваемых правил подобраны **на train** по
перцентилям, итоговая проверка — **на test**.

## 4. Сколько это стоит команде (порог «≥ 4 правила»)

| Показатель | Значение |
|---|---:|
| Алертов в день (медиана) | 131 |
| Алертов в день (максимум) | 166 |
| Проверок на 1 реальный случай | 14.9 |
| Аналитиков нужно (по 30 алертов/день) | **4.4** |

Отобранные жадным алгоритмом 5 правил дают **33.7 % recall при 76 алертах в день**
— то есть двумя аналитиками. Это и есть рабочая точка отсчёта для модели.

## 5. Методологические выводы

1. **Порог «из головы» не работает.** Первая версия правила «fan-out: ≥ 20
   получателей» срабатывала на **99.9 % транзакций** — потому что на полном
   объёме у среднего счёта 55 связей. Пороги обязаны быть квантилями,
   посчитанными на train.
2. **Порог по числу сработавших правил — это и есть бизнес-решение.** k = 1 даёт
   recall 82 % и 2 300 алертов в день; k = 4 даёт recall 30 % и 131 алерт в день.
   Выбор зависит от стоимости часа аналитика и штрафа за пропуск.
3. **Порог выбираем на val, честную оценку делаем на test.** Разница между
   val и test оказалась небольшой (36.1 % → 29.5 % recall), то есть правила
   не переобучились.
4. **Accuracy не считаем вообще**: при 0.1 % отмываний «ничего не нашли» = 99.9 %.

## 6. Что дальше

Этап 4 — ML-модель. Цель, сформулированная в бизнес-терминах: **при том же
бюджете алертов (≈ 0.5 % трафика) поднять recall выше 33.7 %**, в первую очередь
на типологиях, где правила дают 0 % (Smurfing, Bipartite, Gather-Scatter,
Stacked Bipartite).
